## Inventory summary

### API and runtime

The route dispatcher is in `src/api.rs::route`. It implements health/readiness, OpenAPI/docs, diagnostics, watch, JSON/SSE search, catalogue routes, anime/details/episode routes, source discovery, playback aliases, audio, subtitles, downloads, and transcode. The OpenAPI document is generated by `src/api.rs::openapi()` rather than a separate file.

### Providers

The source tree contains MovieBox, 4KHDHub with HubCloud/HubDrive/GreenMotors resolver code, Dramachi, CircleFTP, DhakaFlix, TV/M3U, and addon adapters. Provider dispatch is implemented in `src/service.rs` and `src/providers/mod.rs`.

### Data and caching

Release and playback caches are in-memory maps in `ApiState` (`src/api.rs`). Release cache keys include provider, subject, season, and episode. Release entries have a 600-second TTL and a nominal capacity of 2048 entries. Playback entries have a 120-second TTL and a nominal capacity of 2048 entries. Filesystem caches are implemented in `src/cache.rs` for provider metadata, streams, captions, addons, images, and local state.

### Network and security

Shared HTTP client construction and DNS filtering are in `src/net.rs`. The client uses rustls, public-destination filtering in the custom resolver, connection pooling, a 15-second connect timeout, and redirect syntax validation. Transcode destinations add DNS/IP validation in `src/api.rs`. The DASH/HLS sidecar proxy is bounded by request-line/header limits, manifest/segment byte limits, segment concurrency, cache limits, and idle timeouts in `src/proxy.rs`.

### Deployment

`render.yaml` builds with `cargo build --release --locked`, but starts with `cargo run --release`. This rebuild/checks Cargo metadata at service startup despite the release binary already being built. The configured health check is `/health` and the service receives `$PORT`/Render port configuration.

## Confirmed findings

### C-1 — Search eligibility does not enforce the strict codec policy

**Severity:** High / product correctness  
**Evidence:** `src/api.rs::release_has_usable_source` only checks that a mirror URL is non-empty and passes `validate_url_syntax`. It does not inspect `Release::codec`, media metadata, or a verified final stream. The existing regression test `search_source_eligibility_requires_a_valid_mirror_url` explicitly treats a release with `codec: None` and a valid URL as usable. Provider parsers can populate `H.265`, `HEVC`, `x265`, `H.264`, `x264`, `AV1`, or no codec.  
**Impact:** Under the requested strict Android policy, a confirmed HEVC source can be considered eligible and an unknown codec can be implicitly accepted as playable.  
**Repair direction:** Introduce one shared conservative codec classification function. Reject confirmed HEVC/H.265/AV1 and unknown codec values from the *verified compatible search set*; accept only confirmed H.264/AVC/x264 metadata for the strict policy. Preserve source metadata and report unknown/incompatible states rather than rewriting them.

### C-2 — Search source-check concurrency is request-local

**Severity:** Medium / scalability  
**Evidence:** `src/api.rs::eligible_search` creates `Arc::new(Semaphore::new(SEARCH_SOURCE_CHECK_CONCURRENCY))` for every request. The limit is therefore eight tasks per request, not eight tasks across the process. `ApiState` already owns shared semaphores for transcode and API connections but not source eligibility.  
**Impact:** Concurrent users can multiply expensive provider detail/release checks and amplify upstream load.  
**Repair direction:** Add a shared `Arc<Semaphore>` to `ApiState`, initialize it once, and use it for expensive eligibility checks. Keep the per-request deadline and bounded task creation.

### C-3 — Render startup command repeats Cargo work

**Severity:** Medium / deployment efficiency  
**Evidence:** `render.yaml` uses `buildCommand: cargo build --release --locked` followed by `startCommand: cargo run --release`. `src/main.rs` confirms the actual executable is `moviebox-tui`.  
**Impact:** Startup can spend unnecessary time invoking Cargo and resolving/building instead of executing the already-built binary.  
**Repair direction:** Change only the Render start command to `./target/release/moviebox-tui` after verifying Render's build/runtime filesystem contract. This is a deployment configuration change, not a provider behavior change.

### C-4 — Provider-dependent search has a large worst-case work scope

**Severity:** Medium / latency  
**Evidence:** `catalog_item_source_eligibility` fetches details, enumerates every episode in every returned season, and checks episode releases sequentially until one usable source is found. The enclosing per-item budget is 45 seconds, while each release check has a 15-second timeout. `eligible_search` creates one JoinSet task for every candidate returned by all configured providers.  
**Impact:** Series with many episodes can consume substantial latency and upstream work before search completes. This is partially bounded by the 45-second item deadline and the eight-per-request semaphore, but it is not globally bounded and does not yet have measured before/after evidence.  
**Repair direction:** Measure the current behavior first, then apply a bounded candidate/episode verification policy that preserves the verified-source requirement, stops on a proven eligible source, and cancels unnecessary work safely.

## Suspected or unresolved findings

- Release and playback caches do not coalesce concurrent misses; simultaneous requests can repeat the same upstream operation. This is an optimization candidate, not yet confirmed as a production bottleneck.
- The release cache stores successful empty release lists but does not cache provider errors. The semantics are safer than caching transient failures, but negative-cache behavior should be documented and tested explicitly.
- `probe_media` depends on an external `ffprobe` executable. The local environment can build the application, but the Render configuration does not install or verify ffprobe. Track routes and strict runtime codec inspection therefore require deployment verification before being called production-ready.
- The OpenAPI document and README route table are broad and need an automated route-parity comparison against the dispatcher. Existing unit tests cover selected OpenAPI paths, but do not prove every path/method/response contract.
- The local Naruto search timeout may be caused by upstream availability or the current provider configuration. It must not be classified as a confirmed provider defect without per-provider timing logs.

## Security baseline

No source change weakened TLS verification, redirect validation, public-IP filtering, or header redaction during the baseline. The code contains explicit rejection for private/local destinations and sensitive public headers. Remaining audit work must verify redirect DNS/rebinding behavior, transcode limits, manifest/segment target validation, request-size limits, and secret-safe logging with focused tests.

## Prioritized repair order

1. Add strict, shared codec classification and deterministic H.264/HEVC/unknown eligibility tests.
2. Move source-check concurrency control into shared `ApiState` and add a contention regression test.
3. Add low-overhead timing instrumentation for total request, provider calls, eligibility checks, cache hits/misses, and resolution outcomes without logging signed URLs.
4. Measure cold/warm search, details, episodes, sources, and playback locally with bounded provider access; separate provider failure from code latency.
5. Add route/OpenAPI parity checks and update route documentation from actual dispatcher behavior.
6. Audit cache miss coalescing, signed URL expiration, and playback cache semantics.
7. Update `render.yaml` to execute the verified release binary directly and document ffprobe/runtime assumptions.
8. Run focused live resolver and provider smoke tests, then the full deterministic and release validation suite.
9. Produce the remaining required audit reports and final acceptance report. Do not declare Render or Hostinger production-ready without actual deployment evidence.

## Baseline conclusion

The branch is buildable and its deterministic tests are green, but the backend is **not yet fully production-ready under the new strict acceptance criteria**. The most important confirmed correctness gap is codec-aware search eligibility; the most important confirmed scalability gap is request-local source-check concurrency; the most important deployment gap is the Cargo-based startup command. These are now ready for small, reviewable repair phases.
