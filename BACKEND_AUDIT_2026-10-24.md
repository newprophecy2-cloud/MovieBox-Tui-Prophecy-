## Executive summary

This repository is a Rust terminal media client/library that also starts a custom HTTP/1.1 API service. It is not currently a PostgreSQL-backed Prophecy Verse catalog service. The API uses provider adapters and in-process maps, with optional Redis limited to a search-result cache. There are no SQL migrations, database tables, durable catalog jobs, admin routes, PostgreSQL dependencies, or separate Web and Android playback APIs in this branch.

The current code has two high-priority mismatches with the supplied requirements. First, source eligibility rejects explicit H.265/HEVC labels but treats missing/unknown codec labels as usable and several playback paths bypass that eligibility helper entirely. Second, `src/remux_cache.rs` stores completed MP4 remuxes on disk (up to 2 GiB per entry and 3 GiB total by its limits), while remux preflight creates a temporary MP4 file. These behaviors must be addressed before claiming conformance with the no-unverified-codec and no-persistent-media-output policies.

The larger catalog requirements cannot be implemented safely as a blind patch: they imply a new authoritative data model, migrations, import source selection, authentication, and API contracts that do not exist in this project. The safe sequence is to complete focused correctness/security repairs against the current architecture, then make an explicit architecture decision before adding a persistent catalog service.

## Persistence, Redis, providers, playback, and security findings

### Data and cache

- There is no permanent catalog store, database connection pool, schema, migration runner, catalog transaction, pending import table, or durable catalog job table.
- In-memory caches store search results, provider releases, and resolved playback URLs; TTLs are defined in `src/api.rs`.
- Optional Redis is used only for JSON search-cache `SETEX`/read operations, not catalog truth, rate limiting, pending jobs, or playback-session coordination. Failure degrades to memory.
- Filesystem caches in `src/cache.rs` are used by provider/TUI data paths, including provider metadata, stream, caption, addon, image, and user-local state. They are distinct from the remux video cache but require careful secret/TTL review in a later phase.

### Codec and playback

- `release_has_usable_source` in `src/api.rs` requires a syntactically valid mirror and rejects explicit HEVC/H.265/x265, but accepts codec `None` and other unclassified values.
- `api_sources` serializes all provider releases without that eligibility filter. Direct stream/playback and `/sources/{id}` paths select releases independently; the global H.265 and unknown-codec policy is therefore not enforced across public availability and playback.
- Provider codec labels are not universally confirmed by FFprobe. FFprobe is used in track discovery and remux preflight but is not a general verification gate before all direct playback responses.
- Web and Android are not separate API contracts. Current playback shares provider resolution and response logic.
- Playback routes perform provider discovery/resolution in some flows, which conflicts with the requested stored-source-only playback model.

### Remux/media persistence

- `src/remux_cache.rs` is a filesystem cache. It writes `.fragmented.part`, final `.mp4`, metadata, lock, and temporary finalization files under the application cache; configured limits are 2 GiB per output and 3 GiB total, with two-hour TTL.
- `src/api.rs` routes use that cache for completed remux output and byte-range seeking. Live FFmpeg output is also streamed through a pipe, but the cache writes media chunks to disk while building.
- Remux preflight uses a `tempfile` MP4 for a short FFmpeg output and probes it with FFprobe.
- The API limits concurrent remux slots to two per process. This is a local limit, not a measured capacity result.

### Security/resilience controls observed in source

- Request headers are capped at 64 KiB and request reads are timed; concurrent API connections are capped at 256.
- Remux slots are bounded; FFmpeg invocation uses `tokio::process::Command` rather than a shell.
- Shared network helpers validate public URLs and reject internal/private IP destinations; selected endpoints perform DNS/IP checks and hide sensitive headers in responses.
- No admin auth is present because no admin API exists. The HTTP listener itself has no TLS; production TLS must be terminated by an external reverse proxy/platform.
- No dedicated route-contract, PostgreSQL, Redis-failure, authorization, or global HEVC-bypass tests are identified in the current source inventory. Exact full-suite test status is recorded only after the baseline test command completes.

## Post-audit implementation update

The audit above records the clean `main` baseline at `510a4c0`. The working tree now contains a focused safety/compatibility repair rather than the new PostgreSQL catalog architecture:

- Codec eligibility now fails closed: public source lists retain only releases with recognized non-HEVC codec metadata, preserve each source's original opaque index/fingerprint, and direct playback/source endpoints return stable HTTP 415 errors for explicitly blocked or unverified codecs. The search cache key was versioned to prevent reuse of results from the previous policy.
- Persistent remux MP4 reads and writes were removed from API request paths. Remux FFmpeg output is piped to the live client only; the startup probe is piped in memory with a 32 MiB output cap; startup removes the application-owned legacy `cache/remux` directory where possible. Byte-range remux requests return `501 SEEK_UNAVAILABLE`; ordinary eligible streaming remains available. Regression tests cover disabled cache behavior, rejected compatibility-writer writes, and codec error codes.
- The enabled-provider dispatcher now serves the existing classified K-Drama list and categories handlers at their documented exact root routes. K-Drama detail routes and latest-release listing remain explicitly unsupported.
- README and catalog API documentation now state the current provider-backed/optional-Redis architecture and the no-cache/range behavior. They also identify the missing PostgreSQL schema/migrations, durable imports/jobs, admin authentication/routes, stored-source-only playback, and separate Web/Android contracts rather than claiming these requirements are complete.

Verification performed on the modified working tree: `cargo fmt --all`, `git diff --check`, and `cargo test --locked -- --test-threads=1` all completed successfully (exit code 0). The serial test run is intentional because existing tests mutate process-wide environment variables. Live provider/network tests are marked ignored in the repository and were not run. No HTTP service smoke test, Clippy/all-features matrix, Render or database provisioning, or deployment was performed. This follow-up does not claim full compliance with the broader PostgreSQL-backed catalog requirements.
